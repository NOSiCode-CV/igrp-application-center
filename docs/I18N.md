# Internationalization (i18n)

The Application Center uses **next-intl 4 without i18n routing**: the locale is resolved per request and never appears in the URL.

Spec: `access-management/_specs/i18n/` (`requirements.md`, `plan.md`). The FR-/NFR- tags below point at those requirements.

---

## Model

| Concept | Value |
|---|---|
| Platform languages | `pt`, `en`, `fr` — fixed in code, not configurable per installation (FR-1) |
| Module default | `pt` — the only catalog that must be complete (FR-2) |
| Platform default | `pt` — used only to pick a locale when nothing else is known (OQ-1) |
| Formatting regions | `pt` → `pt-CV`, `en` → `en-GB`, `fr` → `fr-FR` (FR-22) |

**Per-key fallback** (FR-12): requested language → module default (`pt`) → the key itself plus a `console.warn`. The platform default is *not* part of the fallback chain (FR-13).

`en.json` and `fr.json` are **partial by design** (FR-5) — today they only carry the language-selector strings. A screen can therefore mix languages (module text in `pt` next to design-system text in another language); that is accepted, not a bug (FR-14).

### Why there is no locale in the URL

`/[lang]/...` routes are explicitly out of scope (FR-7). HAProxy routes applications by `/apps/[slug]`; a `[lang]` prefix has previously broken that container routing. The locale therefore lives in the session, a cookie and the `Accept-Language` header only — never in the path.

### Locale resolution chain (FR-6)

First match wins; each candidate is normalized to its base language (`pt-CV`, `pt_PT`, `PT-br` → `pt`, FR-8) and non-platform values are skipped:

1. **Session** — `session.locale`, seeded from the OIDC `locale` claim, i.e. the user's `metadata.locale`.
2. **Cookie** — `IGRP_LOCALE`.
3. **`Accept-Language`** request header, honouring q-values.
4. **Platform default** (`pt`).

## Where each piece lives

| File | Responsibility |
|---|---|
| [`src/i18n/config.ts`](../src/i18n/config.ts) | `LOCALES`, `Locale`, `MODULE_DEFAULT_LOCALE`, `PLATFORM_DEFAULT_LOCALE`, `FORMAT_REGION`, `LOCALE_NATIVE_NAMES`, `LOCALE_COOKIE` + options, `isLocale()`, `normalizeLocale()`. Pure module — importable from server components, client components, actions and the Edge middleware. Throws at import time if the module default is not a platform language (FR-3). |
| [`src/i18n/resolve-locale.ts`](../src/i18n/resolve-locale.ts) | `server-only`. `parseAcceptLanguage()`, the pure `pickLocale()` and `resolveLocale()` (session + cookie + headers). |

| [`src/i18n/fallback.ts`](../src/i18n/fallback.ts) | `onIntlError` (missing key → warn; anything else → error) and `getMessageFallback` (renders `namespace.key`). Shared by the request config and the client provider. |

| [`src/i18n/actions.ts`](../src/i18n/actions.ts) | `setLocale` server action. |
| [`src/i18n/global.d.ts`](../src/i18n/global.d.ts) | Declares `next-intl`'s `AppConfig` so `Locale` and message keys are typed from `pt.json`. |
| [`src/i18n/components/i18n-provider.tsx`](../src/i18n/components/i18n-provider.tsx) | `NextIntlClientProvider` + design-system `IGRPI18nProvider`. |
| [`src/i18n/components/locale-switcher.tsx`](../src/i18n/components/locale-switcher.tsx) | The language selector. |
| `src/i18n/messages/{pt,en,fr}.json` | One catalog per language. |

### Wiring

- **`next.config.ts`** — `createNextIntlPlugin("./src/i18n/request.ts")` wraps the config. No `i18n` routing block, no `[locale]` segment.
- **[`src/app/layout.tsx`](../src/app/layout.tsx)** — awaits `getLocale()` + `getMessages()` and wraps `children` in `I18nProvider` inside `IGRPRootLayout`.
- **[`src/lib/auth.ts`](../src/lib/auth.ts)** — `jwt` seeds `token.locale` from the OIDC `locale` claim at sign-in and applies `update({ locale })`; `session` exposes `session.locale`; `getSessionLocale()` reads it null-safely (it only rethrows Next's `DYNAMIC_SERVER_USAGE` bailout, which is control flow).
- **[`src/middleware.ts`](../src/middleware.ts)** — `syncLocaleCookie()` rewrites `IGRP_LOCALE` to the token's locale when they differ (FR-27), reusing the token the auth gate already decoded.
- **[`src/actions/access-client.ts`](../src/actions/access-client.ts)** — `getAccessClientConfig()` sends `Accept-Language: <resolved locale>` next to the bearer token on every API call (FR-9), so the API translates its `detail`s, validation messages and reports.
- **[`src/app/global-error.tsx`](../src/app/global-error.tsx)** — renders outside every provider, so it reads `IGRP_LOCALE` from `document.cookie` and uses an inline `pt`/`en`/`fr` table.

## Using it in code

### Reading messages

```tsx
// client component
'use client';
import { useTranslations } from 'next-intl';

export function UserList() {
  const t = useTranslations('users');
  return <h2>{t('list.title')}</h2>;
}
```

```tsx
// async server component / server action
import { getTranslations } from 'next-intl/server';

const t = await getTranslations('users.invite.accept.loading');
```

Keys are typed from `pt.json` (`global.d.ts`), so `pnpm typecheck` fails on a key that does not exist there.

### Key conventions (FR-34)

- One **top-level namespace per feature**: `common`, `i18n`, `errors`, `users`, …
- **Nested camelCase** keys: `users.list.statusDialog.activateTitle`.
- **ICU** message syntax — arguments, plurals and tags inside the message, never as key suffixes:

  ```jsonc
  "rolesSelected": "{count, plural, one {# perfil} other {# perfis selecionados}}",
  "activateDescription": "Tem certeza que deseja ativar <strong>{name}</strong>?"
  ```

Messages with tags are rendered with `t.rich`:

```tsx
t.rich('list.statusDialog.activateDescription', {
  name: user.name,
  strong: (chunks) => <strong>{chunks}</strong>,
});
```

### Zod schemas are factories

Validation messages come from the catalog, so schemas take a translator instead of holding literals ([`src/features/users/user-schemas.ts`](../src/features/users/user-schemas.ts)):

```ts
export type UsersValidationTranslator = (
  key: keyof Messages['users']['validation'],
) => string;

export const makeEmailSchema = (t: UsersValidationTranslator) =>
  z.email({ message: t('emailInvalid') }).max(254);
```

Call sites build the schema with `useTranslations('users.validation')` (client) or `getTranslations('users.validation')` (server), usually inside a `useMemo`.

### Dates, numbers and sorting

Never hardcode a locale or region (`"pt-CV"`, `"pt-PT"`, `localeCompare(..., 'pt')`, bare `toLocaleDateString()`) in feature code (FR-23). Use the helpers, which pick `FORMAT_REGION[locale]`:

```tsx
// client components and sync server components
const { formatDate, formatDateTime, formatNumber, compare, locale } = useFormat();
formatDate(user.createdAt);        // dd/mm/yyyy
formatDateTime(session.lastSeen);  // dd/mm/yyyy HH:mm
rows.sort((a, b) => compare(a.name, b.name));
```

```ts
// async server components / actions
import { getLocale } from 'next-intl/server';
import { formatDate } from '@/i18n/format';

formatDate(value, await getLocale());
```

`formatDate` / `formatDateTime` return an empty string for missing or invalid input. `compare` is case/accent-insensitive (`sensitivity: 'base'`) and numeric-aware.

## Migrating the next feature

The `users` feature is the reference migration (FR-36). For the next one (`roles`, `permissions`, `departments`, `applications`, `menus`, `files`, `profile`, `settings`):

1. **Add the namespace to `src/i18n/messages/pt.json`** — a top-level key named after the feature, nested camelCase below it, ICU for arguments and plurals. Leave `en.json` / `fr.json` alone unless you are also translating.
2. **Replace the literals** — `useTranslations('<feature>')` in client components, `getTranslations('<feature>')` in server components and actions. Keep the namespace at the feature root and address sub-keys by path (`t('list.title')`), so one hook covers a whole component.
3. **Turn the Zod schemas into factories** taking the validation translator (see above) and build them where the translator is available.
4. **Replace formatting** — swap hardcoded dates/collation for `useFormat()` or `formatDate(value, await getLocale())`.
5. **Map API enum codes to keys** instead of translating them inline. `users` does this in [`src/features/users/lib/i18n.ts`](../src/features/users/lib/i18n.ts) (`userStatusKey`, `inviteStatusKey`, `userStatusLabel`, `useUserStatusOptions`); mirror that shape per feature.
6. **Enable the guard** — add the folder to `MIGRATED_FOLDERS` in [`src/__tests__/i18n/literal-strings.test.ts`](../src/__tests__/i18n/literal-strings.test.ts):

   ```ts
   const MIGRATED_FOLDERS = [
     'src/i18n/components',
     'src/features/users',
     'src/app/(invite)',
     // 'src/features/roles',
   ];
   ```

7. **Run `pnpm test` and `pnpm typecheck`.**

Until a feature is migrated, its hardcoded `pt` text stays as-is (FR-37).

### The literal-string guard (FE-8)

Biome has no equivalent of `eslint-plugin-i18next/no-literal-string`, so the guard is an ordinary Vitest test (NFR-2). It parses every non-test `.tsx` under `MIGRATED_FOLDERS` with the TypeScript compiler API and fails on:

- JSX text containing letters (`<p>Olá</p>`);
- string or template literals rendered as JSX children (`{"Olá"}`);
- string literals in user-facing props — `placeholder`, `title`, `label`, `aria-label`, `aria-description`, `description`, `alt`, `helperText`, `errorText`, `searchText`, `selectLabel`.

Text without letters (symbols, numbers, punctuation) is allowed.

## Adding a key / translating

1. Add the key to **`pt.json`** first — it is the module default and types every key.
2. Use it. `pnpm typecheck` rejects unknown keys.
3. To translate, add the **same key path** to `en.json` and/or `fr.json` with the **same ICU arguments**. Partial files are fine; anything missing falls back to `pt`.

### What the consistency test enforces

[`src/__tests__/i18n/messages.consistency.test.ts`](../src/__tests__/i18n/messages.consistency.test.ts) runs with `pnpm test` (no CI/CD changes, NFR-2) and fails when:

- `en` or `fr` contains a key that does not exist in `pt` (orphan key);
- any value in any catalog is not a string, or does not parse as valid ICU;
- a shared key uses different ICU arguments/tags than `pt`;
- a key segment is not nested camelCase (`^[a-z][a-zA-Z0-9]*$`).

It also prints per-locale coverage (`[i18n] message coverage — pt: 100% …`) as information only; low coverage never fails the build.

### Tests that render translated UI

Use the shared helper [`src/__tests__/helpers/intl.tsx`](../src/__tests__/helpers/intl.tsx), which mounts the same client context as the root layout:

```tsx
import { renderWithIntl } from '@/__tests__/helpers/intl';

renderWithIntl(<UserList users={users} />);          // pt, real catalog
renderWithIntl(<UserList users={users} />, { locale: 'en' });
renderWithIntl(<X />, { messages: { users: { list: { title: 'X' } } } });
```

Defaults to `pt` with the real merged catalog, so assertions can use the actual strings.

## Language selector

[`LocaleSwitcher`](../src/i18n/components/locale-switcher.tsx) is an `IGRPSelect` listing the languages under their native names (`Português`, `English`, `Français` — deliberately untranslated). It is mounted on:

- [`src/app/(auth)/login/page.tsx`](<../src/app/(auth)/login/page.tsx>) — login;
- [`src/app/(invite)/layout.tsx`](<../src/app/(invite)/layout.tsx>) — the public invitation flow;
- [`src/app/(igrp)/(home)/profile/page.tsx`](<../src/app/(igrp)/(home)/profile/page.tsx>) — the authenticated profile page.

**Not in the header.** FR-24 asks for the authenticated header / user menu, but the header is rendered by the framework (`getHeaderData` in `src/igrp.template.config.ts`) and offers no extension point for custom items (OQ-2). The profile page is the agreed interim placement; the header selector moves with the framework phase.

### What changing the language does

1. The `setLocale` server action validates the value against the platform languages (FR-11).
2. When signed in, it persists the preference through `PUT /api/users/me/locale` (stored in `metadata.locale`, FR-10). On failure nothing else changes and the selector shows `i18n.localeSwitcher.changeError`.
3. It writes the `IGRP_LOCALE` cookie (`path=/`, one year, `SameSite=Lax`, not `httpOnly` so `global-error.tsx` can read it).
4. Back in the component, when the action reports `authenticated`, next-auth `update({ locale })` refreshes the session token — the change applies **without a new login** (FR-25).
5. `router.refresh()` re-renders the server tree in the new language.

Unauthenticated, only the cookie is written (FR-26).

**Middleware cookie sync** — on every authenticated request `syncLocaleCookie()` rewrites `IGRP_LOCALE` to the session token's locale when they differ (FR-27). The resolver already prefers the session; the rewrite keeps pages rendered *without* a session — login after logout, the invitation flow — in the same language.

### Invitation language

The invite dialog ([`user-invite-dialog.tsx`](../src/features/users/components/user-invite-dialog.tsx)) has an **"Idioma do convidado"** field (`users.invite.form.localeLabel`) over `LOCALES`, preselected with the inviter's current locale (FR-28), and sends `locale` in the invite payload.

## Error handling

`src/config/error-messages.ts` was **removed** (FR-21). The API translates its RFC-7807 `detail` into the request's `Accept-Language`, so the frontend shows it as-is:

- [`extractApiError`](../src/lib/utilities.ts) returns `problemDetail.detail` when present.
- [`useErrorCopy`](../src/components/errors/use-error-copy.ts) drives the error boundaries: a known framework `IgrpError.code` maps to `errors.codes.<key>`; otherwise the API `detail` / `AppError` public message; otherwise the generic `errors.unexpected`. Generic per-status client fallbacks are not API messages and are ignored.
- [`StatusErrorPage`](../src/components/errors/status-error-page.tsx) takes the title from `errors.status.<401|403|404|500|503|fallback>` and uses the API `detail` as the description when there is one.
