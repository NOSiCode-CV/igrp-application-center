# Internationalisation (i18n)

The template uses **next-intl 4 without i18n routing** through `@igrp/framework-next/i18n`: the locale is resolved per request and never appears in the URL.

## Model

| Concept | Value |
|---|---|
| Platform locales | `pt`, `en`, `fr`. Fixed; an app may enable fewer (`locales` in `src/i18n/index.ts`). |
| Default locale | `pt`. Its catalog (`messages/pt.json`) is complete and types every key. |
| Format locales | `pt-CV`, `en-GB`, `fr-FR` by default; per deployment via `IGRP_FORMAT_LOCALES` (always region-qualified: `pt-PT`, never `pt`). Drive dates, numbers, the design-system locale and `<html lang>`. |
| Resolution | **cookie-first**: `IGRP_LOCALE` cookie → `session.user.locale` → `Accept-Language` → default. An app that persists the choice (`persistLocale`) becomes **session-first**; see the framework spec. |

## Where each piece lives

| File | Role |
|---|---|
| `src/i18n/index.ts` | `igrpDefineI18n(...)`: locales, format locales from the env, `getSessionLocale`. Server-only (reads the session). |
| `src/i18n/request.ts` | next-intl request config, registered by `createNextIntlPlugin` in `next.config.ts`. Must receive the same `i18n` object as `igrpBuildConfig`. |
| `src/i18n/actions.ts` | `setLocale` server action, passed to `IGRPLocaleSwitcher`. |
| `src/i18n/global.d.ts` | Types `useTranslations` keys from `pt.json` plus the framework namespaces. |
| `src/i18n/messages/{pt,en,fr}.json` | App catalogs. One top-level namespace per feature, nested camelCase keys, ICU. |
| `src/igrp.template.config.ts` | `igrpBuildConfig({ i18n })`: the framework resolves the locale, mounts the providers and sets `<html lang>`. |

The framework ships the `common`, `i18n` and `errors` namespaces, the design-system catalog and the chrome catalog (header, menus, error screens, platform error codes) in all three languages. App keys may shadow framework keys.

## Using it

```tsx
"use client";
import { useTranslations } from "next-intl";
const t = useTranslations("home");
<h2>{t("requestPath.title")}</h2>
```

```ts
import { getTranslations } from "next-intl/server";
const t = await getTranslations("home.layers");
```

Dates, numbers and sorting: `useIGRPFormat()` from `@igrp/framework-next/i18n/client` in client components; `igrpFormatDate(value, formatLocale)` from `@igrp/framework-next/i18n` on the server with `await igrpResolveFormatLocale(i18n)`. Never `useFormatter` / `getFormatter` from next-intl and never a hardcoded locale (`new Intl.NumberFormat("pt-PT")`, `toLocaleDateString("pt-PT")`): `pnpm lint:i18n` rejects both in the folders it checks.

Plural messages include `=0` whenever the count can be 0, because next-intl receives the bare base locale (`pt` uses Brazilian plural rules, where 0 is `one`): `{count, plural, =0 {nenhum item} one {# item} other {# itens}}`.

Zod schemas take a translator (`(key) => string`) instead of literals; enum codes from the API map to keys in a small per-feature `lib/i18n.ts`.

## Changing the language

`IGRPLocaleSwitcher` is mounted in the header `actions` slot and on the login page. It calls `setLocale`, which validates, writes the `IGRP_LOCALE` cookie (path `/`, one year, shared by every IGRP app on the host) and refreshes the server tree. `global-error.tsx` renders outside every provider and reads the cookie itself.

## Session-first

An app that persists the language choice (`persistLocale`) is session-first: `session.user.locale` wins over the cookie. This template is cookie-first, so the middleware only carries this as a comment. Middleware (Edge: import from `@igrp/framework-next/i18n`, never from `@/i18n`):

```ts
import { IGRP_LOCALES, igrpSyncLocaleCookie } from "@igrp/framework-next/i18n";
const LOCALE_SYNC = { locales: IGRP_LOCALES, resolution: "session-first" } as const;
// …at the end of the authenticated branch:
return igrpSyncLocaleCookie(request, nextWithPath(), token.locale, LOCALE_SYNC);
```

Switcher wrapper (client), so the session reflects the change without a new login:

```tsx
const { update } = useSession();
<IGRPLocaleSwitcher
  action={setLocale}
  onChanged={async (locale, persisted) => {
    if (!persisted) return;
    const user = (await update({ locale }))?.user;
    if (!user || !("locale" in user) || user.locale !== locale) {
      throw new Error(`Session locale not updated to ${locale}`);
    }
  }}
/>
```

`onChanged` must return the `update` promise. `igrpRunLocaleChange` awaits it before `router.refresh()`; a fire-and-forget `void update(…)` lets the refresh render with the old session locale, so the page stays in the previous language.

`update()` resolves `null` instead of rejecting when the session can't be written (e.g. the session store is down), so check the result and throw. When `onChanged` throws after a persisted change, the switcher rolls the profile and cookie back to the previous locale, skips the refresh and shows its error state, so the user never sees the language change "by itself" at the next sign-in.

`persistLocale` must resolve `false` without calling the API when there is no session (login and invite pages).

## Checks

`pnpm lint:i18n` (also in `build`): `igrp-i18n check-catalogs` (orphan keys, invalid ICU, argument parity with `pt`, keys missing from a non-default locale (opt out with `--allow-missing`), camelCase segments, coverage) and `igrp-i18n check-literals` over the migrated folders. Add a folder to the script when you migrate it; the `(demo)` pages are not migrated.

## Adding a key

1. Add it to `pt.json`. 2. Use it (`tsc` rejects unknown keys). 3. Translate in `en.json` / `fr.json` with the same ICU arguments; `check-catalogs` fails on keys missing from a non-default locale (opt out with `--allow-missing`).
